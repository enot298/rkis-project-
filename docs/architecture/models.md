# Модели данных (схема v1.1)

Версия 1.1 · Основа: «ER-диаграмма и схема БД» v1.0 от 16.10.2026 (задание 3). Код: `django/apps/*/models.py`.

## 1. Модели по приложениям

| Приложение | Модель (таблица) | Назначение |
|---|---|---|
| `accounts` | `User` (user) | Учётная запись и роль: `admin`, `manager`, `storekeeper`, `accountant` |
| `accounts` | `Session` (session) | Сеанс входа с JWT-токеном (BR-005) |
| `customers` | `Client` (client) | Клиент: ФИО/название, телефон, email, адрес |
| `catalog` | `Product` (product) | Товар: цена, остаток на складе, штрихкод |
| `orders` | `Order` (order) | Заказ: клиент, менеджер, статус, сумма, флаги, версия |
| `orders` | `OrderItem` (order_item) | Позиция заказа: товар, количество, цена на момент заказа |
| `orders` | `Payment` (payment) | Платёж по заказу (1:1) |

## 2. Политика удаления (on_delete)

| Связь | on_delete | Почему |
|---|---|---|
| Order → Client | CASCADE | Схема, раздел 6.1: удаление клиента удаляет его заказы. **Риск:** удалённого клиента не вернуть вместе с заказами, поэтому на боевом сервере права на удаление клиентов стоит ограничить (предложение к блоку 6) |
| Order → User (manager) | SET_NULL | BR-006: заказы не удаляются вместе с менеджером, а помечаются `archived` (сигнал) |
| OrderItem → Order | CASCADE | Позиция не существует без заказа |
| OrderItem → Product | PROTECT | Нельзя удалить товар, который есть в заказах (история заказов должна сохраняться) |
| Payment → Order | CASCADE | Платёж не существует без заказа |
| Session → User | CASCADE | Сеансы удаляются вместе с пользователем |

## 3. Ограничения в БД

| Таблица | Ограничение | Имя в БД |
|---|---|---|
| user | роль из списка | `user_role_valid` |
| user | логин уникален | UNIQUE (`username`) |
| session | токен уникален | UNIQUE (`token`) |
| session | **один активный сеанс на пользователя (BR-005)** | `uniq_active_session_per_user` (частичный UNIQUE, `is_active = true`) |
| session | срок действия позже создания | `session_expires_after_created` |
| client | email уникален (пустой = NULL) | UNIQUE (`email`) |
| product | цена ≥ 0, остаток ≥ 0 | `product_price_gte_0`, `product_stock_gte_0` |
| product | штрихкод уникален (NULL допускается) | UNIQUE (`barcode`) |
| order | сумма ≥ 0; статус из списка | `order_total_gte_0`, `order_status_valid` |
| order_item | пара (заказ, товар) уникальна | `uniq_order_item_order_product` |
| order_item | количество > 0; цена ≥ 0 | `order_item_quantity_gt_0`, `order_item_price_gte_0` |
| payment | один платёж на заказ | UNIQUE (`order_id`) |
| payment | сумма ≥ 0; способ и статус из списков | `payment_amount_gte_0`, `payment_method_valid`, `payment_status_valid` |

Валидаторы полей (проверяются в формах и в `full_clean()`): `MinValueValidator` у денег и количеств, `RegexValidator` у телефона клиента, `UnicodeUsernameValidator` у логина.

## 4. Служебные поля

| Поле | Где | Поведение |
|---|---|---|
| `created_at` | user, session, client, product, order | `auto_now_add`, в админке только чтение |
| `updated_at` | client, product, order | `auto_now`, в админке только чтение |
| `version` | order | Растёт на 1 при каждом изменении через `save()`, не редактируется вручную (BR-008) |
| `archived` | order | Признак архивного заказа (BR-006, ручное архивирование) |

Мягкое удаление (`is_deleted`) схемой v1.0 не предусмотрено и не вводилось: роль «архив» выполняет `Order.archived`.

## 5. Вычисляемые значения (по запросу ФР)

| Что | Где | Зачем |
|---|---|---|
| `OrderItem.line_total` | свойство | Сумма по позиции: количество × цена |
| `Order.calculate_total()` | метод | Сумма позиций (используется для кеша `total_amount`) |
| `Order.items_count` | свойство | Число позиций в заказе |
| `Order.is_editable` | свойство | Можно ли редактировать (запрещено в «Выполнен» и «Отменён») |
| `Order.has_big_discount()` | метод | Есть ли позиция со скидкой > 30% (BR-007) |
| `Session.is_expired` | свойство | Истёк ли сеанс |
| `str()` всех моделей | метод | Читаемое представление: «Заказ №5 от 25.10.2026», «Иванов (Менеджер)» |

## 7. Порядок работы с базой

1. Миграции применяются **до** загрузки данных: `python manage.py migrate`.
2. Фикстуры QA загружаются после первой стабильной версии моделей и только на чистую базу (см. `tests/fixtures/README.md`).
3. После изменения моделей: `python manage.py makemigrations`, затем `migrate`. Файлы миграций коммитятся вместе с моделями.
4. Если модели сильно менялись и данные тестовые, проще пересоздать базу: удалить `db.sqlite3`, `migrate`, `loaddata`.
