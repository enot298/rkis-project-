# Трассировка бизнес-правил: правило → механизм → проверка

Обновление матрицы из блока 3 (раздел 8 схемы БД). Версия 1.1. Составил ТЛ совместно с БР.

Принцип: правила, которым нужны данные одной записи или БД, проверяются в модели (в несколько уровней). Всё, что зависит от запроса, пользователя или HTTP-ответа, проверяется в API (этап Э7), и это помечено явно.

## Матрица

| Правило | Где реализовано | Уровни защиты | Тест |
|---|---|---|---|
| **BR-001** Дата заказа не в прошлом | `Order.clean()`: при создании дата ≥ сегодня. Старые заказы редактировать можно | Модель/форма админки. В API — тот же `full_clean()` при создании (Э7) | `OrderRulesTests.test_br001_*` |
| **BR-002** «Выполнен» → «Отменён» запрещено | `Order.clean()` (сообщение в форме) и `Order.save()` (защита вне формы) | Форма + `save()`. Массовое действие админки перехватывает ошибку | `test_br002_*` |
| **BR-003** Сумма > 100 000 ₽ → `needs_approval` | `Order.recalculate()` вызывается сигналом при любом изменении позиций. Порог — `APPROVAL_AMOUNT_THRESHOLD`, условие «строго больше» | Сигнал + кеш в БД. Снять флаг может только человек (действие «Подтвердить») | `test_br003_*` |
| **BR-004** Товара на складе не хватает | `OrderItem.clean()`: учитывается остаток; при правке позиции сравнивается только прирост | Форма админки. **Отложено в API:** списание остатка при создании заказа и защита от гонки двух запросов (транзакция + блокировка строки, этап Э7). На уровне БД остаток не может стать отрицательным (`product_stock_gte_0`) | `OrderItemRulesTests.test_br004_*` |
| **BR-005** Один активный сеанс на пользователя | Частичный UNIQUE в БД (`uniq_active_session_per_user`) + `Session.clean()` | БД + форма. **В API (Э7):** при входе старый сеанс завершается или вход отклоняется (решение закрепить в API-контракте) | `test_br005_*` |
| **BR-006** Пользователь удалён → заказы `archived` | `pre_delete` сигнал в `orders/signals.py` + `Order.manager` с `SET_NULL` | Сигнал + FK. Заказы не теряются | `test_br006_*` |
| **BR-007** Скидка > 30% → подтверждение | `Order.has_big_discount()` сравнивает цену в позиции с ценой товара; флаг ставит `recalculate()`. Порог `DISCOUNT_THRESHOLD`, «строго больше» | Сигнал. **Допущение:** скидка = снижение `price_at_moment` относительно `product.price`; отдельного поля скидки в схеме нет | `test_br007_*` |
| **BR-008** Версия не совпадает → 409 | `Order.version` растёт при каждом `save()`; `Order.ensure_version()` бросает `OrderVersionConflict` | Модель даёт механизм. **HTTP 409 формирует API (Э7)**: клиент передаёт версию, сервер вызывает `ensure_version()` | `test_br008_*` |

## Дополнительные ограничения (не из списка BR)

| Ограничение | Механизм | Тест |
|---|---|---|
| Количество в позиции > 0 | CHECK в БД + валидатор | `test_zero_quantity_rejected_by_db` |
| Позиция товара в заказе не повторяется | UNIQUE (order, product) | `test_unique_product_per_order` |
| Один платёж на заказ | `OneToOneField` | `test_one_payment_per_order` |
| Нельзя удалить товар из заказов | `PROTECT` | `test_product_in_order_cannot_be_deleted` |
| Удаление клиента удаляет заказы | `CASCADE` (по схеме) | `test_deleting_client_cascades_to_orders` |
| Телефон только цифры, 7–15 | `RegexValidator` | `ClientTests.test_phone_validation` |
| Email уникален без учёта регистра | `Client.save()` приводит к нижнему регистру | `test_email_is_lowercased_and_unique` |
| Отмена заказа требует причину | `Order.clean()` | `test_cancel_requires_reason_in_clean` |

Тесты лежат в `django/apps/orders/tests.py`, запуск: `python manage.py test`.
